Jurati
Shared team memory for people and AI agents
520 tests 14 core modules ~1,600 lines of core Apache 2.0 Python 3.13+ MCP native

Git-backed knowledge repo + MCP server. Your agents read the team's decisions before every session — and write back through branches and PRs, never by silently mutating your source of truth.

The Problem

Every agent session starts cold

Teams adopting AI agents today have no shared memory. Each agent session begins from scratch. Decisions get re-debated. In-flight work gets trampled. Conventions get ignored. A developer on Claude Code makes a decision at 2 PM — the developer on Cursor at 3 PM has no idea it happened.

The bigger the team, the worse the drift. Three agents working in parallel can produce three contradictory implementations of the same thing — because none of them knew about the others.

The Solution

Agents that remember what the team knows

Jurati gives your team a shared knowledge repository backed by git. Agents read decisions, workflows, active work, and team principles before every session. When an agent captures something worth sharing, it goes through branches and pull requests — the same review process your code uses.

No separate tool. No context switch. The agent already knows someone switched the session store last week, that there's an open PR migrating the module you're about to touch, and that the team agreed to use gRPC for inter-service calls.

Compatibility

Works with any agent

Jurati uses MCP (Model Context Protocol), so it works with any agent that speaks the protocol. Claude Code, Copilot, Cursor, or your own tooling — all connect to the same knowledge repo.

Each agent identifies itself with a client slug. Short-lived active context is namespaced so agents don't step on each other. Everything above that — decisions, workflows, principles, search results — is shared across the entire team.

A team with three developers on three different tools all writes to the same knowledge repo, sees each other's decisions, and benefits from the same team memory.

Knowledge Types

Five types of team knowledge

Entries are markdown files with structured frontmatter, organized by how durable and consequential they are:

Principle
Long-lived standards that span projects. "We use gRPC for inter-service calls."
Decision
Design choices with rationale and alternatives considered.
Workflow
Team processes — review gates, release steps, naming conventions.
Project
What's in flight, what's blocked, cross-project dependencies.
Active
Short-lived notes — current investigations, handoffs. Opt-in, 7-day max TTL.
Governance

Progressive ceremony

Low friction for low-stakes content. High ceremony for high-stakes decisions. The escalation level controls how content enters the knowledge repo — not whether it can.

L0
Active
Ephemeral refs, no PR, auto-expires. Opt-in only.
L1
Project
Branch + lightweight PR. Auto-merge eligible.
L2
Workflow
Branch + PR. Human review required.
L3
Principle
Branch + PR. Human review required. Highest ceremony.
Privacy

Privacy by design, not by policy

Jurati is architecturally constrained to not track the things that surveillance-adjacent systems track. This isn't a policy — the code physically cannot do it.

  • ×No query logging — what you search for is never stored
  • ×No read receipts — no one knows what you've read
  • ×No participation metrics — no "engagement" dashboards
  • ×No presence signals — no "who's active" tracking
  • ×No activity inference — git provenance is never repurposed as participation data
  • ✓Git commits exist for accountability — who wrote what and when
  • ✓PRs exist for review — the same process your code uses
  • ✓Restricted entries are invisible to search — only accessible by explicit ID
Getting Started

Three commands to shared memory

Zero-config start. Progressive opt-in to advanced features as your team grows.

1
pip install jurati

Install the package. Python 3.13+ required.

2
jurati init

Scaffolds a knowledge repo structure — or connects to an existing one.

3
jurati serve

Starts the MCP server. Point your agent at it and go.

Later, opt into L0 active context, PR signal classification, integration contracts, and event emission as your needs grow. Nothing is required upfront.

Architecture

Pure core / IO boundary split

Jurati enforces a hard architectural boundary: core/ is pure, deterministic, and has zero I/O imports (enforced by AST guard in tests). All I/O lives in git/ and providers/. The MCP server is orchestration glue.

core/ Pure, deterministic, zero I/O
←
server.py MCP tool handlers
→
git/ Clone, fetch, commit, PR
providers/ Signal protocol + GitHub impl

Current time, repo snapshots, and config enter core as explicit function arguments. The core never reaches out for them. This makes every core function trivially testable — no mocks, no fixtures, no monkey-patching.

Data Model

Schema v2

Entries are Pydantic models with structured frontmatter. Schema v2 added visibility, recorded_by, and sensitivity enforcement — all backward compatible with v1 entries via Pydantic defaults.

class Frontmatter(BaseModel):
  schema_version: int = 2
  id: str                     # ^[a-z0-9][a-z0-9-]{2,120}$
  title: str
  type: EntryType             # principle|decision|workflow|project|active
  level: EscalationLevel      # L0|L1|L2|L3
  visibility: Visibility      # internal|external
  sensitivity: Sensitivity    # normal|internal|restricted
  recorded_by: RecordedBy | None
  source: SourceMeta | None   # git provenance (repo, commit, author)
  review: ReviewMeta
  ...

Visibility is an explicit author declaration, not inferred. Sensitivity controls search exclusion — restricted entries are invisible to BM25, context, and search. RecordedBy tracks which MCP client submitted the write — mechanical fact, not authorship.

Write Pipeline

Intent → Materialize

Writes follow a two-phase pattern. Pure planning in core produces intent objects. Materialization in the I/O layer commits them atomically with event records.

record() / propose()
→
plan_record() / plan_propose()
→
WriteIntent
→
materialize_write()
→
git commit + event

plan_record() handles L0/L1 entries. plan_propose() handles L2/L3. Higher-stakes tools cannot create lower-stakes content and vice versa. The intent object carries all validation results — materialization is a pure commit operation.

Search

BM25 with multi-signal scoring

Search uses a full BM25 inverted index with four scoring signals multiplied together:

combined = bm25 × recency × type_weight × repo_affinity × exact_boost

bm25: Okapi BM25 (k1=1.5, b=0.75)
recency: exp(-0.693 × age_days / 14)
type_weight: principle=1.4, decision=1.2, ..., active=0.8
repo_affinity: same-repo=1.5, dependency=1.2, other=1.0
exact_boost: ID or title match = 10x

The inverted index is cached on ServerState and invalidated on sync(). Restricted entries are excluded from the index entirely — not just filtered from results. Titles are triple-weighted in the document representation.

Integration

Integration contract — four access modes

External systems consume Jurati knowledge through a stable contract with named access modes. Each mode applies progressively stricter filtering:

Access Mode Visibility Branch Restricted Use Case
CONTEXT all all excluded MCP tools (default)
EXTERNAL_CONTEXT external only all excluded Cross-system context sharing
GATE_EVIDENCE external only source-of-truth only excluded Governance / gate systems
DURABLE_SOURCE all source-of-truth only excluded Auditing, compliance

Non-CONTEXT modes require a system_id. Identities crossing the boundary are salted via opaque_identity() to prevent cross-system correlation.

Coordination

Signal classification

PR activity and other coordination signals are classified into six deterministic effects with urgency and confidence scores. The classification is pure — no LLM, no heuristics beyond configurable keyword sets.

continueKeep going, no conflict
reuseLeverage existing work
reviseUpdate your approach
pauseStop and wait
handoffTransfer to another agent
clarifyNeed more information

Signals flow through a provider protocol (SignalProvider). GitHub PRs are the first implementation. The protocol is runtime-checkable — add Linear, Jira, or Slack signals by implementing fetch_signals() and needs_refresh().

Privacy Architecture

What the system refuses to track

Privacy in Jurati is not a policy layer — it's an architectural constraint. The server physically cannot persist or report these categories of data:

  • ×Query text — search terms are never logged or stored
  • ×Read patterns — no read receipts, no "who viewed this"
  • ×Participation metrics — no contribution counts, no engagement scores
  • ×Absence signals — no "hasn't contributed in X days"
  • ×Agent activity — nothing outside explicit tool calls

At integration boundaries, opaque_identity() salts identities per requesting system. System A cannot correlate identities from System B's responses. L0 entries produce no events. Restricted entries are excluded from the BM25 index — not just filtered from results, but never indexed.
