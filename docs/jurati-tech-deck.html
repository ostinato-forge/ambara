How Jurati Works

One ambient signal becomes shared agent context.

Jurati is a small MCP runtime around a git-backed knowledge repo. Any connected agent pointed at the same remote reads the same team context before work starts.

Runtime Boundary

Humans do not operate the API. Agents do.

The visible workflow is a person labeling a Git pull request or speaking normally to an agent. The agent uses Jurati's MCP tools behind the scenes.

1
MCP client connects to server.py.The server loads config from environment, clones or reuses the knowledge repo cache, fetches main, and builds the runtime index used for MCP calls.
2
Agent calls sync() and context().The client instructions say to do this before work starts, then summarize only the relevant coordination facts to the person.
3
Agent may call record() or propose().Those are typed write APIs for agents, not extra controls the person has to remember.

Read Path

Startup context is rebuilt from git, then served from a runtime index.

The server treats git as the source of truth and keeps only rebuildable local state: a repo cache, the runtime index for MCP calls, and optional derived SQLite/FTS read models.

Key boundary: core indexing and ranking logic consumes plain data. Network, git, and filesystem work stay outside the core modules.

Knowledge Model

Everything durable is a markdown entry with schema v2 frontmatter.

Entries are typed so agents can tell the difference between a durable decision, a workflow, a project update, and a short-lived handoff.

Type Default Level What It Means
activeL0Short-lived current work, opt-in active refs, requires expiry.
projectL1Project state, blockers, and near-term context.
workflowL2Team process that should be reviewed before it becomes durable.
decisionL2/L3Design choice with rationale and consequences.
principleL3Long-lived engineering rule or standard.

Ambient PR Signals

The label path is deliberately narrow.

GitHub PRs enter Jurati only when they carry the configured label, defaulting to jurati. Draft PRs are not special-cased today; if GitHub returns the labeled PR as open, it is treated as open coordination context.

Coordination Classifier

PRs turn into concrete guidance, not generic alerts.

The classifier is deterministic. It looks at state, path overlap, target areas, and configured keyword groups, then returns an effect with urgency, confidence, and evidence.

pauseOpen labeled PR overlaps requested paths. Agent should avoid editing that target until it accounts for the PR.
reuseMerged labeled PR overlaps requested paths. Agent should inspect and build on that work.
reviseTitle or excerpt contains decision, workflow, migration, release, security, or architecture language.
handoffTitle or excerpt signals ownership, review, blocker, assignment, or waiting state.
continueSame repo, different area. Keep it as background context.
clarifyPotentially relevant but ambiguous. Ask only if ambiguity blocks a safe plan.
EvidenceRepo, PR number, URL, title, author, state, updated time, matched paths, and reason.
PrivacyGuidance includes the narrow privacy boundary alongside the results.

Search and Context

Search is ranked, but restricted knowledge is never indexed.

search() uses BM25 with recency, type, repo affinity, and exact-match boosts. query() tries simple topic matching first, then falls back to BM25. 

# src/jurati/core/scoring.py
combined =
  bm25
  * recency_half_life_14_days
  * type_weight
  * repo_affinity
  * exact_match_boost

restricted entries:
  excluded before BM25 index construction

title text:
  weighted by appearing three times in document text

Write Path

Writes are planned in pure code, then materialized through git.

The server never directly mutates main. Core code returns an intent; the git layer creates commits, refs, branches, or pull requests.

Privacy Boundary

The architecture limits what Jurati can know.

Jurati is a broadcast system for explicit team context, not an observation system. The server status payload and context guidance both state this boundary.

NO
No broad miningOnly configured repos and labeled PRs are used for PR coordination.
NO
No read receiptsThere is no surface for who viewed an entry or which agent read what.
NO
No participation trackingGit provenance exists for accountability, not engagement analytics.
ID
Restricted entries stay out of broad contextThey are excluded from context, search, and the BM25 index, but explicit read(id) can still fetch them.

Engineering Shape

The codebase is split around side effects.

The important design choice is not the exact client. It is the separation between pure policy logic, server orchestration, provider reads, and git writes.

core/Schema, validation, indexing, search ranking, signal classification, write-intent planning. No network or git side effects.
server.pyMCP tool handlers, lifecycle state, sync health, BM25 cache, coordination assembly, write orchestration.
providers/External signal adapters. GitHub PRs ship today; the provider protocol is the shape for more sources.
git/Clone, fetch, branch lifecycle, commits, active refs, PR creation, and branch-only fallback.
Short version: agents get a stable MCP surface; teams get a reviewable git source of truth; humans keep using their normal PR workflow.
