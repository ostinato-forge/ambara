# Ambara v0.6.0 Plan

Status: next feature release plan
Updated: 2026-06-03

## Answer

Ship Ambara v0.6.0 as a multi-forge foundation release with first-class GitLab
support.

Do not position this release as "every git platform now works equally well."
That would overclaim the product and blur the engineering target.

The sharper and more honest release shape is:

- GitHub remains first-class
- GitLab becomes first-class
- the core review/write/signal model becomes forge-aware instead of
  GitHub-shaped
- other forges become easier to add later, but are not claimed as first-class
  in v0.6.0

## Product Read

Ambara's idea is broader than GitHub.

The product promise is reviewable project context for humans working through
coding agents. If the durable context layer feels "fully real on GitHub, but
branch-only everywhere else," Ambara reads narrower than the actual idea.

That matters because many of the teams who most need provenance, review, and
human-inspectable context are on GitLab or self-hosted forge infrastructure.

So the goal of v0.6.0 is not generic platform checkboxes. It is to remove
"GitHub-only" from the product's center of gravity while keeping the same
truth-first standards that shaped v0.5.1.

## Release Shape

v0.6.0 should deliver four things:

### 1. Forge-aware review lifecycle

Ambara should understand that "review" is the product concept and "pull
request" or "merge request" is the forge-specific implementation.

Build:

- generic remote parsing and forge detection
- a forge abstraction for review creation, stale-review listing, and compare
  URLs
- response and receipt language that is truthful for both PR and MR flows

### 2. First-class GitLab write path

GitLab should work as a real Ambara target, not just a branch-only remote.

Build:

- GitLab auth discovery and token handling
- merge request creation for durable writes
- stale MR listing for hygiene
- compare/review links for branch-only fallback where needed

### 3. First-class GitLab signal path

Project signals should not be hardwired to GitHub PRs plus Jira.

Build:

- GitLab review signal ingestion
- generalized review signal data model
- coordination guidance that works across GitHub PRs and GitLab MRs
- docs/config that explain review signals in forge-neutral terms

### 4. CI and onboarding truth

The documented setup paths should match the supported platforms.

Build:

- keep GitHub Action capture as first-class
- add GitLab CI capture guidance or entrypoint support
- onboard/docs/examples for GitLab remotes
- support claims that distinguish first-class, compatible, and not-yet-smoked
  surfaces

## Why GitLab First

GitLab is the right next target for three reasons:

- it materially expands the reachable user base, including self-hosted teams
- its merge request model is close enough to GitHub's that Ambara's write and
  review semantics still make sense
- it forces the right abstraction boundaries without requiring a fully generic
  "support every forge and every workflow engine" rewrite

## Must Change In The Codebase

These are the current GitHub-shaped seams that should drive the v0.6.0 work.

### A. Auth and remote parsing are GitHub-specific

Today:

- `parse_github_remote()` only recognizes `github.com`
- auth discovery is built around `gh auth status` and GitHub token env vars

Implication:

- non-GitHub remotes degrade early into branch-only behavior
- forge support cannot be added cleanly without untangling auth from provider
  logic

Required outcome:

- generic remote parsing plus explicit forge detection
- per-forge auth candidate generation
- shared review lifecycle entrypoints above forge-specific adapters

### B. Review creation is GitHub-specific

Today:

- PR creation posts to `api.github.com`
- CLI fallback uses `gh pr create`
- branch-only compare links are generated as GitHub compare URLs
- hygiene stale-review listing uses `gh pr list`

Implication:

- the durable write path is first-class only on GitHub

Required outcome:

- a forge adapter interface for create-review, list-open-reviews, and
  branch-only review URLs
- a GitLab implementation beside GitHub

### C. Review signals are typed as GitHub PRs

Today:

- provider aggregation is "GitHub PRs plus Jira"
- `PRSignal.provider` is `Literal["github"]`
- many tests and payload examples assume GitHub URLs and `pull/`

Implication:

- the core coordination layer is more generic than the type system and
  provider edge imply

Required outcome:

- a generalized review signal shape for forge-backed review artifacts
- GitHub and GitLab adapters mapping into that shape
- classification logic that remains pure and mostly unchanged

### D. CI capture and docs are GitHub-centered

Today:

- the bundled CI path is a GitHub Action entrypoint
- tokenized remote rewriting is GitHub-specific
- README and install docs assume GitHub examples

Implication:

- even where the core repo model is forge-neutral, the product feels GitHub-led

Required outcome:

- clear separation between "GitHub Action capture" and generic CI capture
- GitLab CI support or a documented GitLab CI path
- first-class GitLab onboarding and examples

## Engineering Plan

### Workstream 1. Forge abstraction layer

Build:

- `ForgeKind` detection from remote URL
- generic remote parser returning forge, host, namespace, repo
- review lifecycle protocol above GitHub/GitLab implementations
- generalized review result types replacing GitHub-shaped naming where it leaks

Acceptance:

- no top-level write orchestration path has to special-case GitHub directly
- branch-only fallback still works on unknown forges without false claims

### Workstream 2. GitLab durable write support

Build:

- GitLab auth discovery and token env support
- merge request creation via GitLab API or CLI-compatible path
- stale MR listing for hygiene
- GitLab compare URLs for branch-only fallback

Acceptance:

- a GitLab-backed knowledge repo can produce reviewed durable writes
- hygiene can see open stale GitLab review artifacts
- receipts distinguish MR creation from branch-only fallback

### Workstream 3. Review-signal model and GitLab signals

Build:

- generic review signal model
- GitHub adapter refactor onto that model
- GitLab review signal adapter
- provider config/docs that describe review signals and Jira as separate signal
  families

Acceptance:

- `context()` coordination can surface GitHub or GitLab review signals with the
  same guidance semantics
- provider failures remain isolated by adapter

### Workstream 4. CI and onboarding truth

Build:

- GitLab CI capture path or documented CI wrapper using the capture pipeline
- GitLab remote examples in onboarding and install docs
- release proof additions for GitLab-backed write flow
- support matrix in docs: first-class, compatible, not yet smoked

Acceptance:

- a GitLab team can follow docs without translating GitHub-specific assumptions
- product docs stop implying that the only real review path is GitHub

## Explicit Non-Goals For v0.6.0

Not in scope unless needed as a narrow enabler:

- first-class Bitbucket support
- first-class Azure DevOps support
- full Gitea or Forgejo support
- replacing Jira with a larger general provider marketplace
- a hosted Ambara control plane
- major retrieval/ranking redesign
- broad UI work beyond what onboarding, receipts, and static surfaces need

## Product Positioning Changes

v0.6.0 should shift public language from "GitHub plus some compatibility" to
"reviewable context across first-class forges."

Keep:

- git-backed reviewed knowledge
- human-verifiable proof
- explicit writes and truthful receipts
- compact context over full memory dumps

Tighten:

- review is the concept; PR and MR are forge-specific forms
- GitHub and GitLab are first-class
- other forges may work at the repo/branch layer without being claimed as
  first-class review surfaces

## Release Bar

v0.6.0 is done when all of the following are true:

- a GitLab remote can be onboarded without GitHub-specific edits
- `propose()` can open a GitLab merge request for durable writes
- hygiene can inspect stale GitLab review artifacts
- GitLab review signals can influence coordination guidance
- CI capture has a documented or built GitLab path
- docs and receipts never imply GitHub when the forge is GitLab

## Suggested Issue Breakdown

- umbrella: multi-forge foundation + first-class GitLab
- forge abstraction for review lifecycle
- GitLab durable write and hygiene support
- generalized review signals plus GitLab signal adapter
- GitLab CI/onboarding/docs truth pass
