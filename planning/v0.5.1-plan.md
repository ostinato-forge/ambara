# Ambara v0.5.1 Plan

Status: follow-up release plan
Updated: 2026-06-03

## Answer

Ship Ambara v0.5.1 as a truth-and-reliability release.

v0.5.0 established the product and open source release bar. v0.5.1 should not
expand Ambara into a bigger product. It should make the existing promise more
trustworthy:

- the human is the user
- the agent is the operating surface Ambara must steer
- reviewable context should behave consistently across MCP, CLI, file, import,
  capture, and action paths
- proof and docs should lead with the surfaces that reduce dependence on
  perfect agent behavior

This release should tighten correctness, reduce misleading success states, and
make the product story sharper without changing the core product boundary.

## Product Read

Ambara is still reviewable project context for AI coding agents, but the real
user is the human developer or team using those agents.

That means the hardest product problem is not storage or ranking. It is whether
Ambara can reliably influence heterogeneous agents enough that the human gets:

- continuity across sessions
- provenance and review for durable context
- restraint around stale, conflicting, or sensitive context
- predictable write ceremony when the user says "save this" or "record that"

v0.5.1 should therefore optimize for reliability at the human experience layer,
not for breadth.

## Release Goals

### 1. Make write outcomes honest

The product should never imply a PR exists when only a branch or compare URL
exists. The human should be able to trust Ambara's confirmation text.

Build:

- distinct receipts for actual PR creation versus branch-only fallback
- explicit branch-only language in MCP and CLI responses
- proof that agents and humans can tell which ceremony actually happened

### 2. Align safety across all write paths

The action and capture paths should not have a weaker safety envelope than the
interactive CLI or MCP flows.

Build:

- content-policy parity for commit capture and GitHub Action capture
- explicit documentation of what is blocked, escalated, reviewed, or allowed
- proof fixtures for sensitive-but-not-secret content, not only regex secrets

### 3. Make the GitHub Action path real

The action path should clone or reuse the knowledge repo correctly, authenticate
explicitly, and push in a way that matches the documented inputs.

Build:

- a complete action bootstrap path from `knowledge_remote` and `knowledge_token`
- explicit auth wiring for clone/fetch/push
- action-level proof that a clean runner can capture and push review branches

### 4. Reduce dependence on soft agent compliance where possible

Ambara will always need to steer agents, but v0.5.1 should lean harder on
surfaces that make the product useful even when agent behavior varies.

Build:

- stronger positioning for `ambara demo`, static HTML, CLI reads, and file
  outputs
- clearer docs that the human can inspect the knowledge state directly
- proofs that do not depend only on "the agent followed the instruction"

### 5. Consolidate duplicated orchestration logic

Signal refresh and adjacent orchestration logic should have one canonical path
so behavior stays consistent and easier to reason about.

Build:

- one shared signal refresh path used by snapshot, coordination, and curation
- one error-handling story for unavailable signal providers
- tests that prove behavior through the shared path

## Must Fix In v0.5.1

These are release-driving items because they affect product trust or make a
documented path incomplete.

### A. Branch-only fallback honesty

Current problem:

- Ambara can return `status: "ok"` with branch-only fallback and phrasing that
  sounds equivalent to a PR-backed review step.

Required outcome:

- branch-only responses explicitly say that no PR was created
- review URLs are labeled as compare/review links, not PRs
- confirmation copy matches reality across MCP, CLI, and any proofs

### B. Action bootstrap and push path

Current problem:

- the GitHub Action path accepts `knowledge_remote` and `knowledge_token`, but
  the capture entrypoint currently relies on a local repo path and does not
  clearly bootstrap the cached repo from the declared remote inputs

Required outcome:

- the action clones or reuses the knowledge repo from `AMBARA_KNOWLEDGE_REMOTE`
- the action can authenticate clone/fetch/push from `AMBARA_KNOWLEDGE_TOKEN`
- the action path is verified on a clean runner, not assumed from local state

### C. Content-policy parity for capture/action writes

Current problem:

- commit capture currently applies secret scanning and escalation, but not the
  fuller content-policy review/block/warn behavior used elsewhere

Required outcome:

- capture and action writes share the same content safety contract as CLI/MCP
- docs describe the contract once, not differently by entry path
- tests cover non-secret sensitive content in capture flows

## Strong Should-Fix Items

These are not product-boundary changes, but they meaningfully improve trust,
maintainability, or proof quality inside the existing product.

### Signal refresh deduplication

- remove duplicated refresh logic across coordination, curation, and snapshot
- centralize health/error/cache updates
- keep one canonical unavailable-state behavior

### Human-visible proof tightening

- extend release proof to cover branch-only fallback wording
- add action-path proof or a documented runner smoke
- add capture-path content-policy proof

### Documentation emphasis shift

- lead docs and launch copy more clearly with `ambara demo`
- keep static HTML visible as a human-inspectable surface
- explain that MCP is first-class, but not the only way to inspect or use
  Ambara context

### Smaller correctness and maintainability cleanup

- replace or narrow broad exception swallowing where it can mask product truth
- remove type ignores when a safe assertion or cast is clearer
- split very large modules only where it improves ownership of real subsystems
  rather than churn for its own sake

## Explicit Non-Goals For v0.5.1

Do not turn this release into a bigger roadmap bundle.

Not in scope unless a blocking dependency emerges:

- new hosted/cloud product surfaces
- package family split
- new provider families beyond the existing GitHub/Jira line
- major schema redesign
- full rethink of escalation levels
- large UI build beyond the existing static HTML surface
- broad retrieval algorithm rewrite

## Product Positioning Changes

v0.5.1 should sharpen the story, not replace it.

Keep:

- reviewable git-backed project context
- compact startup over full-dump memory
- explicit writes, review for durable changes, local proof, privacy boundary

Tighten:

- the human is the user; the agent is the delivery surface
- Ambara is strongest where the human can verify outputs directly
- success means the human can trust what happened, not only that the agent got
  a plausible-looking response

Lead more clearly with:

- `ambara demo`
- static HTML browsing
- CLI/file-based inspection
- receipts that say what actually happened

## Engineering Plan

### Workstream 1. Honest write receipts

- update response copy for branch-only fallback
- ensure field names distinguish PR URLs from compare/review URLs
- add tests for all write modes
- update release proof to verify response wording

### Workstream 2. Action and capture parity

- bootstrap knowledge repo in the action path from remote inputs
- wire auth for clone/fetch/push explicitly
- route capture writes through shared content-policy checks
- add clean-runner or fixture-based tests for action capture

### Workstream 3. Shared signal refresh path

- consolidate refresh logic into one helper used by snapshot/coordination/curation
- preserve mute-policy behavior and health accounting
- add regression tests for unavailable, empty, cached, and refreshed states

### Workstream 4. Docs and proof refresh

- add a `v0.5.1` release notes draft
- update release proof to include new trust/correctness checks
- update README/doc ordering if needed so demo/proof/human-visible surfaces are
  easier to find than deep reference material

### Workstream 5. Focused cleanup

- tighten exception handling where it affects user-visible truth
- remove the most misleading ignores or duplicated glue
- only split modules where the cut line is clear and low-risk

## Release Bar

Ambara v0.5.1 is ready only when all of this is true from the built artifact
or documented runner proof, not only from source inspection:

- branch-only fallback is explicit and not presented like a PR
- GitHub Action capture can bootstrap, authenticate, and push as documented
- capture/action writes obey the same content-policy contract as CLI/MCP writes
- signal refresh behavior is consistent across snapshot, coordination, and
  curation surfaces
- `ambara demo` and static HTML remain working and documented as first-class
  human verification surfaces
- source tests, lint, type checks, and build still pass
- release proof covers the new trust-sensitive paths

## Suggested Sequence

1. Fix branch-only honesty first.
2. Make the action path real from declared inputs.
3. Unify content-policy behavior across capture/action and interactive writes.
4. Consolidate signal refresh logic.
5. Refresh proof docs and release notes.
6. Take small cleanup items only if they support the above work.

## Definition Of Done

v0.5.1 is done when Ambara more reliably delivers its existing promise:

- the human can trust what Ambara says happened
- all documented write paths behave like one product
- the product is easier to verify without perfect agent obedience
- the follow-up release reads as a hardening pass, not a scope sprawl release
